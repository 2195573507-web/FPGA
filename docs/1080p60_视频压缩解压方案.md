# 1080p60 定速率帧内视频压缩/解压方案设计

> 适用平台：RK3568_MES2L100H（RK3568J + 紫光同创 Logos-2 PG2L100H-6IFBG484）
> 链路：PC --1GbE--> FPGA --> 像素流
> 文档性质：方案设计（含本地真实视频实测数据）

---

## 0. 一页纸摘要

| 项目 | 结论 |
|---|---|
| 原始 4:2:0 8bit 码率 | 12.00 bit/px = **1493 Mbit/s**，占千兆口 **156%** → **必须压缩** |
| 1GbE 可用预算 | **957.1 Mbit/s = 7.69 bit/px**（MTU1500，含全部协议开销） |
| 最低压缩比需求 | **1.56 : 1**（极其温和） |
| 实测无损码率 | **4.26 bit/px = 530 Mbit/s = 占 1GbE 55%**（MED+Rice，8 个真实视频实测） |
| 硬件最坏情况上界 | **6.00 bit/px = 746.5 Mbit/s = 占 1GbE 78%**（固定 4bit 量化兜底） |
| 延迟 | **小于 1 行**（约 15 us），无帧间依赖 |
| 行缓存 | 约 **3.75 KB**（Y 平面 2 行），**不占用 DDR3** |
| 解码吞吐 | 186.6 Msample/s → 建议 **2 路并行 @ 93.3 MHz** |

**核心结论：只需 1.56:1 的压缩比。方案采用「MED 帧内预测 + Rice 熵编码 + 固定位宽兜底」，实测无损即达 2.3:1。硬件仅需行缓存，完全绕开 DDR3 带宽与帧间参考帧管理，且具有可证明的码率上界。**

## 1. 需求与链路预算

### 1.1 视频参数

| 参数 | 值 |
|---|---|
| 分辨率 | 1920 x 1080 |
| 帧率 | 60 fps |
| 有效像素率 | 1920x1080x60 = **124.416 Mpx/s** |
| 采样格式 | YCbCr 4:2:0，8 bit |
| Y 采样率 | 124.416 Msample/s |
| Cb / Cr 采样率 | 各 31.104 Msample/s |
| **总采样率** | **186.624 Msample/s** |

> ⚠️ **真正的吞吐瓶颈是 186.6 Msample/s 的采样率，不是比特率。** Rice 解码是变长逐样本操作，必须按采样率而非比特率做时序预算。详见 §8.4。

### 1.2 以太网载荷预算

1GbE + UDP + MTU1500。每包固定开销 = 8B 前导 + 12B IPG + 14B 以太头 + 20B IP 头 + 8B UDP 头 + 4B FCS = 66 B。

| 帧类型 | UDP 净荷 | 总开销 | 效率 | 可用载荷 |
|---|---|---|---|---|
| MTU1500 | 1472 B | 1538 B | 95.71% | **957.1 Mbit/s** |
| Jumbo | 8972 B | 9038 B | 99.27% | 992.7 Mbit/s |

**取 MTU1500（不依赖交换机 Jumbo 配置）：预算 = 957.1 Mbit/s**

### 1.3 压缩比需求

| 源格式 | 裸流 bit/px | 裸流 Mbit/s | 占 1GbE | 需压缩 |
|---|---|---|---|---|
| RGB888 | 24 | 2986 | 312% | 3.12:1 |
| YCbCr 4:4:4 10bit | 30 | 3732 | 390% | 3.90:1 |
| YCbCr 4:2:2 10bit | 20 | 2488 | 260% | 2.60:1 |
| YCbCr 4:2:2 8bit | 16 | 1991 | 208% | 2.08:1 |
| **YCbCr 4:2:0 8bit** | **12** | **1493** | **156%** | **1.56:1** |

> **决策：先降到 4:2:0（色度 2x2 平均），压缩比需求从 2.08:1 降到 1.56:1。** 这是性价比最高的一步：色度下采样是纯硬件操作（3 次加法 + 1 次右移 2 位），零算法复杂度，却省掉 25% 码率。

## 2. 方案总览

### 2.1 数据流

```
┌───────────── PC 侧编码器 ─────────────┐
│  RGB 帧 → YCbCr 4:2:0 → 条带切分      │
│     ↓                                  │
│  MED 帧内预测 → 残差 → 符号折叠        │
│     ↓                                  │
│  码率控制器（Q 自适应，预算跟踪）      │
│     ↓                                  │
│  Rice 熵编码 / 固定位宽兜底            │
│     ↓                                  │
│  条带头 + UDP 封包                     │
└────────────────┬───────────────────────┘
                 │ 1GbE（典型 530 Mbit/s，硬上界 746.5 Mbit/s）
┌────────────────▼───────────────────────┐
│         FPGA 解码器（PG2L100H）        │
│  UDP/MAC 接收 → 包重排 → 条带头解析    │
│     ↓                                  │
│  Rice 解码 → 残差反折叠                │
│     ↓                                  │
│  MED 重建（仅需 2 行行缓存，BRAM）     │
│     ↓                                  │
│  色度上采样 4:2:0 → 4:4:4              │
│     ↓                                  │
│  像素流输出（RGB888 / 4:2:2 / 后级）   │
└────────────────────────────────────────┘
```

### 2.2 与 H.264 方案对比

| 维度 | 本方案 | H.264 解码 |
|---|---|---|
| 帧间依赖 | **无**，每帧独立 | 有参考帧管理，需整帧 DDR 往返 |
| 延迟 | **小于 1 行（约 15 us）** | 一整帧 + 重排序（33 ms 以上） |
| 内存 | **约 3.75 KB 行缓存** | 多参考帧，MB 级 |
| DDR3 往返 | **不需要** | 必然需要 |
| 运算 | 比较器 + 加减法器 + 移位，**无乘法器** | CABAC/CAVLC + 反变换 + 去块滤波 |
| 开源 RTL | 有成熟参考 | 检索证实基本不存在 |
| 专利 | 自研格式，无专利池 | H.264 专利池授权 |
| 压缩比 | 2.3:1（无损） | 约 100:1 |

> **关键判断：本项目只需要 1.56:1，H.264 的 100:1 能力完全用不上，却要付出帧间依赖、DDR 带宽、专利和开源 RTL 缺失的全部代价。**

## 3. 格式定义

### 3.1 色彩空间转换（编码端）

BT.601 studio swing，定点整数实现：

```
Y  = (( 66*R + 129*G +  25*B + 128) >> 8) + 16
Cb = ((-38*R -  74*G + 112*B + 128) >> 8) + 128
Cr = ((112*R -  94*G -  18*B + 128) >> 8) + 128
```

### 3.2 4:2:0 下采样

Cb/Cr 按 2x2 块平均（box filter），除 4 用右移 2 位实现：

```
Cb_420[y][x] = (Cb[2y][2x] + Cb[2y][2x+1] + Cb[2y+1][2x] + Cb[2y+1][2x+1]) >> 2
```

### 3.3 平面组织

**三个平面顺序编码**（Y 全帧 → Cb 全帧 → Cr 全帧），而非交错。原因：

- 每时刻只需维护**一个平面**的 2 行行缓存 → 内存减半
- 各平面可独立并行解码 → 便于提高吞吐
- 与 JPEG/JPEG-LS 一致，参考实现可复用

| 平面 | 尺寸 | 样本数/帧 |
|---|---|---|
| Y | 1920 x 1080 | 2,073,600 |
| Cb | 960 x 540 | 518,400 |
| Cr | 960 x 540 | 518,400 |
| **合计** | | **3,110,400** |

## 4. 帧内预测：MED 预测器

采用 JPEG-LS 的 **MED（Median Edge Detector）** 预测器。选定理由：**精度高（实测残差熵最低）、无乘法器、因果（仅用已解码样本）、硬件极简。**

### 4.1 预测公式

邻域布局（当前样本 x）：

```
      c │ b
     ───┼───
      a │ x
```

- a = 左邻，b = 上邻，c = 左上邻

```
if      c >= max(a, b):  pred = min(a, b)
else if c <= min(a, b):  pred = max(a, b)
else:                    pred = a + b - c
```

### 4.2 硬件实现

只需：2 个比较器 + 1 个加减法器 + 1 个三路选择器。**无乘法器、无除法器、无查找表。**

### 4.3 边界处理

- 每行第一个像素：a = 上一行同列样本（退化为纯垂直预测）
- 第一行：b = c = 128（中灰），仅用左邻预测
- **规则必须编码端与解码端完全一致**（可复现性要求）

### 4.4 实测效果

8 个 1080p 视频实测的平均一阶熵（bit/sample）：

| 分量 | 直接传（无预测） | 左邻 DPCM | **MED 二阶** |
|---|---|---|---|
| Y | 7.27 | 3.96 | **3.09** |
| Cb (4:2:0) | 5.30 | 1.82 | — |
| Cr (4:2:0) | 4.74 | 1.49 | — |

> MED 比简单左邻预测好约 22%，硬件成本几乎相同。**采用 MED。**

## 5. 残差处理与熵编码

### 5.1 残差与符号折叠

残差 r = x - pred，范围 -255..+255。折叠为非负整数（几何分布，利于 Rice 编码）：

```
u = (r >= 0) ? (2*r) : (-2*r - 1)
```

反折叠：

```
r = (u & 1) ? -((u+1) >> 1) : (u >> 1)
```

### 5.2 Rice 编码

参数 k（每行/每片自适应，0..8）：

```
编码:  q = u >> k;  rem = u & ((1<<k)-1)
       码字 = q 个 0 + 一个 1 + k 位 rem
       码长 = q + 1 + k

解码:  数前导 0 得 q; 读 k 位得 rem; u = (q << k) | rem
```

### 5.3 自适应 k 的选择

编码端按**行**统计残差均值，选使总码长最小的 k：

```
k_opt = argmin_k  SUM_i [ (u_i >> k) + 1 + k ]
```

硬件上可用均值估计近似（k ≈ log2(mean(u))）。**k 写入条带头，解码端直接使用，无需自适应算法。**

### 5.4 实测码率（核心数据）

**MED + Rice，无损，8 个真实 1080p 视频实测：**

| 视频 | 4:2:0 (bit/px) | 4:2:2 (bit/px) | Mbit/s | 占 1GbE |
|---|---|---|---|---|
| video_111440 | 2.45 | 2.89 | 305 | 32% |
| video_112454 | 4.36 | 4.75 | 543 | 57% |
| video_112507 | 4.43 | 4.80 | 551 | 58% |
| video_112739 | 4.01 | 4.39 | 499 | 52% |
| video_113343 | 4.22 | 4.62 | 525 | 55% |
| video_113421 | 4.27 | 4.68 | 531 | 56% |
| video_113452 | 4.51 | 4.89 | 561 | 59% |
| video_113539 | 4.52 | 4.89 | 562 | 59% |
| **平均** | **4.26** | **4.66** | **530** | **55%** |

**4:2:0 无损 = 530 Mbit/s，仅占千兆口的 55%，余量 45%。**

### 5.5 固定 k 的极简硬件变体

若不做逐行自适应（省去统计逻辑），可用全帧统一 k：

| k | bit/px | Mbit/s | 占 1GbE |
|---|---|---|---|
| 2 | 5.12 | 637 | 67% |
| 3 | 6.23 | 775 | 81% |
| 4 | 7.56 | 941 | 98% ⚠️ |

> **推荐 k=3 作为保守固定值（81%），或做逐行自适应（55%）。**

## 6. 码率控制（关键设计）

> ⚠️ **这是整个方案唯一真正的风险点。** Rice 是变长编码，遇到高熵内容（雪花噪声、强纹理）码率会暴涨。必须设计**可证明的硬上界**。

### 6.1 三档模式

每条带（tile）独立选择编码模式：

| 模式 | 方法 | 码率 | 用途 |
|---|---|---|---|
| **Mode 0** | MED + Rice 自适应 | 实测约 4.26 bit/px | 常规内容（绝大多数） |
| **Mode 1** | MED + Rice + 量化 Q | 可控 3.9-4.0 bit/px | 中等熵内容，质量优先 |
| **Mode 2** | 固定 4bit 量化（无熵编码） | **恒定 6.00 bit/px** | **高熵兜底，硬上界** |

### 6.2 Mode 2 的硬上界推导

```
4:2:0 每像素样本数 = 1.5  (Y 1.0 + Cb 0.25 + Cr 0.25)
Mode 2 每样本固定 4 bit
→ 每像素 1.5 x 4 = 6.00 bit/px
→ 码率 = 6.00 x 124.416 Mpx/s = 746.5 Mbit/s
→ 占 1GbE = 746.5 / 957.1 = 78.0%
```

**结论：无论输入内容如何，链路占用率不超过 78%。这是可证明的硬上界，不依赖内容统计。**

### 6.3 条带结构与预算

**条带（tile）定义：每个平面按 8 行**为一个条带。

| 平面 | 条带尺寸 | 样本数 |
|---|---|---|
| Y | 8 x 1920 | 15,360 |
| Cb | 8 x 960 | 7,680 |
| Cr | 8 x 960 | 7,680 |

每帧条带数 = Y 平面 1080/8 = 135，Cb/Cr 平面各 540/8 = 67.5 → 68，
合计 135 + 68 + 68 = **271 条带/帧**

> ⚠️ **实测校正**：色度平面是 4:2:0 下采样后的 **540 行**（不是 1080 行），
> 故每色度平面只有 68 条带，不是 135。早期文档按「三平面各 135」估成 405，
> 已按真实码流更正。条带号分配：Y `0..134`、Cb `135..202`、Cr `203..270`。

条带预算（按 4:2:0，8 行）：

```
每帧总样本 = 3,110,400
每帧预算 (75% 安全裕度) = 957.1e6/60/8 x 0.75 = 1,494,000 B
每条带平均预算 = 1,494,000 / 271 = 5,513 B
  (但 Y 条带样本数是色度的 2 倍, 实际预算按样本数加权分配, 见 6.4)
```

### 6.4 闭环控制算法

编码端按条带顺序处理，维护全局预算计数器：

```
budget_left = frame_budget
for each tile:
    Q = 1                          # 起始：无损
    encode tile at (Q)
    if bytes(tile) > tile_budget:  # 超预算
        Q = 2;  re-encode
    if bytes(tile) > tile_budget:
        Q = 4;  re-encode
    if bytes(tile) > tile_budget:
        Q = 8;  re-encode
    if bytes(tile) > tile_budget:
        Q = 16; force Mode 2       # 硬上界兜底
    budget_left -= bytes(tile)
    tile_budget = budget_left / tiles_remaining   # 动态再分配
```

**优点：**

- 允许**局部超支**（复杂场景），靠后续简单场景补回
- 最坏情况退化为 Mode 2，码率绝对可控
- 解码端无需知道控制策略，只需读条带头

### 6.5 量化质量实测

| 量化步长 Q | bit/px | Mbit/s | 占 1GbE | PSNR |
|---|---|---|---|---|
| 1（无损） | 3.89 | 484 | 51% | 无损 |
| **2** | 3.89 | 485 | 51% | **45.7 dB** |
| **4** | 4.04 | 503 | 53% | **41.1 dB** |

> **Q=2 达 45.7 dB（影视母版级），Q=4 达 41.1 dB（高质量广播级），均在 53% 链路占用内。**
> Q 取 2 的幂，量化用右移实现，无除法器。

## 7. 码流格式

### 7.1 条带头（16 B）

| 偏移 | 字段 | 位宽 | 说明 |
|---|---|---|---|
| 0 | magic | 16 | 0x4C53 ('LS') |
| 2 | version | 4 | 格式版本 |
| 2 | plane | 2 | 0=Y, 1=Cb, 2=Cr |
| 2 | mode | 2 | 0=Rice, 1=Rice+Q, 2=固定位宽 |
| 3 | k | 4 | Rice 参数 (0..8) |
| 3 | q_shift | 4 | 量化右移位数 (0=无损) |
| 4 | frame_id | 16 | 帧序号（循环） |
| 6 | tile_id | 16 | 条带序号 0..270（Y 0..134 / Cb 135..202 / Cr 203..270） |
| 8 | byte_count | 16 | 本包载荷字节数 |
| 10 | last_in_tile | 8 | 条带内**最后一个包**标志 ⚠️ 每帧有 271 个，不是 1 个 |
| 11 | pkt_idx | 8 | **本条带内的包序号**（0,1,2,…，末包同时置 last_in_tile） |
| 12 | crc32 | 32 | 载荷 CRC32 |

> ⚠️ **`last_in_tile` 的语义极易误读**：它是「该条带的最后一包」，一帧里有 271 个包带此标志。
> 接收端**绝不能**见到它就解码整帧 —— 必须等帧描述符声明的条带全部到齐（见 7.1.1）。
> 这个错误在 PC 端对照实现中真实发生过，导致解码器报 `Rice 位流提前耗尽`。

### 7.1.1 帧描述符包（每帧首个包）

整帧的第一个包，不承载像素，只提供重组所需的最小元数据。载荷 12 B：

| 字段 | 位宽 | 说明 |
|---|---|---|
| magic | 16 | 0x4C53，与条带头一致（双重校验） |
| n_tiles | 16 | 本帧条带总数（= 271，Y 135 + Cb 68 + Cr 68） |
| n_packets | 16 | 本帧包总数（含本描述符包） |
| flags | 16 | bit0 有损 / bit1 含 Mode 2 条带 / bit2 tile_rows≠8 |
| total_bytes | 32 | 本帧 **UDP 应用数据报字节总量**（= 各像素包线上字节之和，每包含 16 B 应用头；**不含 28 B 描述符自身，也不是物理以太网线上字节**）。实测 e2e 帧 0 = 1,197,942 = 1,182,966 像素 payload + 936 × 16 |

- 以 `plane = 3` 标识（0/1/2 已被 Y/Cb/Cr 占用），`tile_id = 0`、`pkt_idx = 0`。
- **完成判据 = 已收条带数 == n_tiles**，与到达顺序无关。
- 描述符在 UDP 乱序中可能**晚于**像素包到达，接收端须能接受后到的描述符（清点既有条带后立即判定）。

### 7.1.2 条带完整性判据（接收端）

单看「收到了这个 tile 的某个包」不足以判断条带可用 —— 丢包可能发生在条带**内部**。
正确判据（由发送端保证 pkt_idx 从 0 连续编号、且仅末包置 last_in_tile 推出）：

```
tile 完整  <=>  见过该 tile 的 last_in_tile 包, 且 已收包数 == 末包 pkt_idx + 1
```

因为 pkt_idx 唯一，故「个数 == 末序号+1」等价于「0..末序号一个不缺」。

**一条带最多几包**：Y 条带 15360 样本、色度条带 7680 样本，载荷按 `MAX_TILE_DATA` = 1456 B
切包。FPGA 侧 `frame_ctrl` 用 **16 位位图**记录条带内已收包序号，**单条带上限是 16 包**。

**真正的最坏情况要按编码器推导，不能用「样本数 / 1456」估算。**

`Tools/fpga_codec.py` 的无损模式（Mode 0，`q_shift=0`）码长上界：

```
plane 是 uint8 (0..255); MED 预测只用左/上/左上, 同为 0..255
  => 残差 r = plane - pred  in [-255, 255]
  => fold(r) = 2r (r>=0) 或 -2r-1 (r<0)  in [0, 510]
  => Rice 码长 cost_k(u) = (u >> k) + 1 + k;  best_rice_k 在 k=0..8 里取总长最小
     单样本代价上界 = min_k cost_k(u) 的最大值 = 10 bit  (u=256 时 k=7 或 8; u=510 时 k=8)
     注: k=8 时 u=510 的码长 = (510>>8)+1+8 = 1+1+8 = 10 bit, 不是 9
  => 整条带总长 <= 15360 x 10 bit = 153600 bit = 19200 B
  => Y 条带上界 = ceil(19200 / 1456) = 14 包;  色度条带 = 7680 x 10 bit = 9600 B = 7 包
```

**所以 Y 条带的编码上界是 19200 B / 14 包**（不是 `ceil(15360/1456)` = 11 包——那个式子把
「15360 个样本」当成了「15360 个字节」，忽略了 Rice 码可能**扩展**到每样本 10 bit）。
上界推导脚本：`_tmp/p4_tilebound.py`（输出 `_tmp/p4_tilebound.txt`）。

实测（全部为无损 Mode 0，`q_shift=0`，1920x1080，`TILE_ROWS=8`，`MAX_TILE_DATA=1456`）：

旧报告里出现过的「15 包」是早期 `MAXPKT=1024` 台架口径（`ceil(19200/1008) = 20`，
或 `ceil(19200/1280) = 15`），与当前 `MAX_TILE_DATA=1456` 的正式工具链**不可比**，已弃用。

**为什么不是 8 包上限**：这是本方案早期的一个错误断言——曾经写成「理论最坏 11 包，仍远小于 255，
8 位 `pkt_idx` 足够」，把**字段位宽**（`pkt_idx` 8 位，确实够）与**接收端位图容量**混为一谈。
FPGA 侧 `frame_ctrl` 早期用 8 位位图，于是**实测真实工具链最坏 7 包已只剩 1 包余量**，
二值噪声 13 包、1 像素棋盘 14 包直接越界。该缺陷由端到端仿真暴露并已修复为 16 位位图（见
`docs/rtl_fix_code_review.md` §2）。

**越界行为是「整帧丢失」，不是「降级」**：`frame_ctrl` 对 `pkt_idx >= 16` 的包把该条带的 `last_idx`
置成非法哨兵 `5'h1F`，于是该条带**永不判完整** ⇒ `tile_ready` 永不脉冲 ⇒ 解码器永不读走 ⇒
`tile_buf` 写满后逐字节丢弃 ⇒ 后续条带连锁失败 ⇒ 整帧丢失。保留该哨兵（而不是静默截断）的目的，
正是把失败模式收敛为「丢一帧」而不是「缓冲溢出后的不确定行为」。

**发送端约束**：`Tools/fpga_codec.py` 必须保证单条带 <= 16 包。16 包容量 = 16 x 1456 = **23296 B**；
实测最坏条带载荷 19200 B（1 像素棋盘），余量 4096 B。若将来 MTU 变小或压缩比进一步变差，
该余量会被吃掉，需要重新核算。

残帧处置（PC 对照实现已按此实现并通过测试）：

| 情形 | 处理 |
|---|---|
| 条带内缺包 / 整条带丢失 | 该帧判为残帧，整帧丢弃（条带独立可解码，但缺块会破坏 4:2:0 行对齐，故不做局部掩盖） |
| 帧落后最新帧超过 2 帧 | 判定为不可补齐，立即计入残帧，不再等待 |
| 超时（默认 0.5 s）未补齐 | 计入残帧 |
| 已解出过的 frame_id 再来包 | 计为重复，丢弃（防重复帧被二次解码） |

> **FPGA 端取舍**：硬件不需要「残帧计数」这类调试设施。实时链路上遇到缺条带，
> 更实用的做法是**整帧不上屏**（或复制上一帧），保证画面不撕裂；但**必须**在
> 每帧开头复位条带接收状态机，否则一次丢包会导致其后所有帧都无法判定完成。

### 7.2 UDP 封装

- UDP 净荷 <= 1472 B（避免 IP 分片）
- 条带头 16 B → 数据载荷 <= 1456 B
- 包数估算：530 Mbit/s / (1456 x 8) = **45.5 kpps**
- 1GbE 线速上限 81 kpps（MTU1500）→ **占用 56%，安全**

### 7.3 解码端重排

- 用 frame_id + tile_id + **pkt_idx** 检测丢包/乱序（见 7.1、7.1.2）
- 条带独立可解码 → 丢失一个条带只影响 8 行
- 无需整帧缓冲，**FIFO 深度只需覆盖网络抖动**（建议 4-8 KB）

**为什么不收集齐整帧再解码**：本方案的条带是「8 行」（Y 平面 1920 B/行），
而一根 DDR3 行缓冲远大于此。保留**条带即到即解**的流式特性，才能让
延迟稳定在 1 行量级（约 15 us）；若改为等整帧到齐，延迟会退化为 16.7 ms（一帧），
等于把方案相对 H.264 最大的优势之一（低延迟、无帧间依赖）白白丢掉。

因此接收端只需按 **frame_id -> tile_id -> pkt_idx** 三级组织，每级用位图或计数表
记录到达情况；**不需要**按序重排整帧数据。

> 代价：画面出现丢包时该帧可能缺块。折中做法是「整帧不上屏」而非「局部掩盖」——
> 见 7.1.2 的 FPGA 端取舍。

## 8. FPGA 解码器架构

### 8.1 模块划分

```
udp_rx           : MAC + UDP 解析, 输出 (tile_id, payload)
pkt_reorder      : 按 tile_id 重排, 输出有序字节流 + 条带头
tile_ctrl        : 条带头解析, 分发参数 (k, q_shift, mode)
bit_unpack       : 位流 -> u 值序列 (变长转定长)
rice_dec         : Rice 解码 (前导零计数 + 提取 rem)
pred_recon       : 反折叠 + MED 重建 (需要行缓存)
line_buffer      : 双行 BRAM (乒乓)
chroma_upsample  : 4:2:0 -> 4:4:4
video_out        : 像素流输出 (DE/HSYNC/VSYNC)
```

### 8.2 行缓存精确计算

MED 需要当前行 + 上一行：

| 平面 | 每行字节 | 2 行合计 |
|---|---|---|
| Y | 1920 | 3840 B |
| Cb | 960 | 1920 B |
| Cr | 960 | 1920 B |

**平面顺序解码 → 峰值 = max(3840, 1920) = 3840 B = 3.75 KB**

若需并发处理色度上采样，加约 1.9 KB 的色度行 FIFO，**总计约 6 KB**，轻松放入 BRAM。

> **重点：完全不触碰 DDR3。** 这绕开了项目中最难的 DDR3 带宽分配与多缓冲 ownership 问题。

### 8.3 解码伪代码

```verilog
// 每个样本一个周期（简化示意）
always @(posedge clk) begin
    // 1. Rice 解码
    u = rice_decode(bitstream, k);      // 前导零计数 + 提取 k 位

    // 2. 反折叠
    r = (u[0]) ? -((u + 1) >> 1) : (u >> 1);

    // 3. 可选反量化
    r = r << q_shift;                   // 左移 = 乘 Q

    // 4. MED 预测（从行缓存取 a, b, c）
    if      (c >= max(a, b))   pred = min(a, b);
    else if (c <= min(a, b))   pred = max(a, b);
    else                       pred = a + b - c;

    // 5. 重建
    x = clamp(pred + r, 0, 255);

    // 6. 写行缓存 + 输出
    line_buffer_write(x);
    pixel_out <= x;
end
```

### 8.4 吞吐与时序预算 ⚠️

**这是最关键的设计约束。** 总采样率 **186.624 Msample/s**：

| 并行度 | 所需时钟 | 评价 |
|---|---|---|
| 1 样本/时钟 | **186.6 MHz** | ⚠️ 对 PG2L100H-6 偏高，时序收敛困难 |
| **2 样本/时钟** | **93.3 MHz** | ✅ **推荐** |
| 4 样本/时钟 | 46.7 MHz | ✅ 舒适，但面积翻倍 |

**2 路并行的实现方法：编码端把每个条带的位流切成 2 条独立子流**（按偶/奇样本交错），解码端用 2 个独立 Rice 解码器并行处理。

> ⚠️ **待确认：PG2L100H-6 的实际可达 Fmax 需用 PDS 综合后确认。** 本机 PDS 仅存有未解压的安装包（D:/PDS/pds_2022.2-sp4.2-ads-win64/.../Setup.exe），未能实测。

### 8.5 位读取器设计要点

Rice 解码的串行瓶颈是「数前导零」。解决方法：

- 一次从 FIFO 加载 **32 bit** 到桶形移位器
- 用**前导零计数（LZC）**组合逻辑一次算出 q（单周期，无循环）
- 处理跨字边界的码字（需回退指针）

**这是唯一需要仔细设计的组合路径**，其余逻辑都很浅。

3. **无 SFP/PHY/光模块真实收包证据**；ARP 到 FPGA 真实对端未执行；`--mode raw`（非管理员）与 `--mode l2`（无 Npcap）均未跑通。

5. **色度上采样算法（浮点 vs 定点）仍未定**，上板 RGB 比对必须声明容差。
6. **16 包上限是结构硬上限**：当前样本实测单条带最高 **14 包**（1 像素棋盘；见 §7.1.2 表）。按编码器推导的 Y 条带估算上界同样是 **14 包**（15360 样本 × 10 bit = 19200 B = `ceil(19200/1456)`）。**「理论最坏 11 包」是早期错误断言，已在 §7.1.2 判错并删除**（它把「15360 个样本」误当成「15360 个字节」，忽略了 Rice 码可扩展到每样本 10 bit）。即便按 14 包，也**不能外推未来内容永不越界**（MTU 变小或压缩比变差都可能越界）；越界在 FPGA 侧的确定语义是**该条带永不判完整**（不产生 `tile_ready`），该帧最终由新帧顶替或看门狗判 `frame_drop`——**不等于越界即刻丢整帧**，且已发布的 `tile_ready` 不可撤回。PC 侧已在组包入口加可诊断拒绝（17 起）。
7. **16 位 frame_id 回绕**在连续 65,536 帧后仍存在**半范围不可消歧**的固有边界（连续漏收 ≥32768 帧无解），收敛手段是**半范围判据 + 超时清理 + 重启时显式复位**（新建 `FrameAssembler`）。**注意：描述符无法用于消歧** —— 描述符的 `total_bytes` 只是咨询量，RTL 侧 `frame_ctrl` 保存但**不据此完成帧**（`rtl/frame_ctrl.v:383-384`），接收端也没有可用于判定「哪一圈」的帧号高位或时间戳，所以**不能靠描述符自校验解决回绕歧义**。本轮修复的是**回绕点的错误丢弃**（`fid <= last_done_fid` 线性比较 ⇒ 所有小于 `last_done` 的号都被误判重复），不是无限失联消歧。
