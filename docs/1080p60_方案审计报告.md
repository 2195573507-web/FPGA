## 一、总体结论
═══════════════════════════════════════════════════════════════════════════

✅ **方案技术可行，设计优秀，主要风险已识别并有缓解措施。**

### 核心优势
1. **压缩比需求温和** - 仅需1.56:1，实测无损达2.82:1，余量充足
2. **硬上界可证明** - Mode 2保证78%链路占用上限，消除码率失控风险  
3. **零DDR3依赖** - 仅3.75KB BRAM，完全绕开最复杂的资源竞争
4. **算法简洁** - 无乘法器、无复杂变换，硬件友好
5. **低延迟** - <1行延迟(15μs)，无帧间依赖

### 主要风险
⚠️ **时序收敛** - 93.3MHz @ PG2L100H-6需实测验证
⚠️ **长序列码率** - 当前数据仅前4帧，需完整视频统计
⚠️ **2路并行细节** - 编码端交错机制需详细设计
⚠️ **PC编码器实时性** - Python难以达到实时，需C++/GPU重写

## 二、关键问题识别
═══════════════════════════════════════════════════════════════════════════

### 1. 🔴 CRITICAL - 文档多处混淆比特率与采样率
**位置**: §8.4

**问题描述**:
文档正确指出"真正的吞吐瓶颈是186.6 Msample/s的采样率，不是比特率"，
但在资源估算和UDP包速率计算中又回到比特率视角。Rice解码是**逐样本串行操作**，
必须保证每秒处理186.6M个样本，无论它们压缩成多少比特。

**影响**: 可能导致时序预算错误估计

**验证**: ✅ 文档§8.4已正确识别，但需在所有章节保持一致


### 2. 🟡 HIGH - 码率数据仅基于前4帧采样
**位置**: §5.4, 附录A

**问题描述**:
8个视频各采样前4帧（共32帧，0.53秒）。真实应用场景可能包含：
  - 场景切换（高熵跳变）
  - 长时间静态场景（低熵）
  - 特效/转场（极高熵）
实测4.26 bit/px可能无法代表长序列统计特性。

**影响**: 码率控制算法可能在长视频中遇到预算枯竭

**缓解措施**: 已有Mode 2兜底(6.00 bit/px)，但会牺牲质量

**行动项**: 补充至少10分钟完整视频的逐秒码率统计


### 3. 🟡 HIGH - 2路并行解码的编码端实现细节缺失
**位置**: §8.4

**问题描述**:
文档提到"编码端把每个条带的位流切成2条独立子流（按偶/奇样本交错）"，
但未说明：
  1. 如何在Rice编码的变长特性下保证2路负载均衡
  2. 偶/奇交错是否破坏MED预测的因果性（需要左邻和上邻）
  3. 解码端如何同步2路并重建正确的空间顺序

**影响**: 实现时可能发现方案不可行，需回退到单路@186.6MHz

**行动项**: 需详细设计2路并行的数据分割与重组机制

## 三、优秀设计亮点
═══════════════════════════════════════════════════════════════════════════

### ⭐ 1. Mode 2硬上界设计

这是整个方案最出色的设计：
  - 固定4bit量化，恒定6.00 bit/px，无论输入内容
  - 数学可证明：1.5 sample/px × 4 bit/sample = 6.00 bit/px
  - 746.5 Mbit/s = 78% of 1GbE，永远不会溢出
  - 完全消除变长编码的最大风险

**对比**: 对比H.264的VBV缓冲区管理，本方案的硬上界更简单且可证明


### ⭐ 2. 完全绕开DDR3

仅需3.75KB BRAM行缓存，完全不触碰DDR3：
  - 无帧缓冲管理复杂度
  - 无DDR3带宽竞争（本板可能有其他模块共享DDR3）
  - 无多缓冲ownership问题
  - 延迟降至1行（约15μs）

**对比**: H.264解码必然需要多参考帧（数MB），DDR3往返不可避免


### ⭐ 3. 条带独立可解码

每个8行条带独立编解码，带来：
  - 丢包影响局部化（仅8行损坏）
  - 可用上一行重复简单掩盖
  - 无整帧缓冲需求
  - 解码器可并行处理多条带（若资源充足）

**鲁棒性**: 网络抖动不会导致整帧失效

**理由**: 这是项目最大的技术风险。如果PG2L100H-6无法在93.3MHz收敛：

**步骤**:

  2. 设置约束：93.3MHz时钟，PG2L100H-6速度等级
  3. 查看时序报告，确认Slack
  4. 若失败，尝试流水线优化或降频

**预计耗时**: 2-4小时


### 🟡 P1 - 近期执行
**基于现有codec_budget_1080p60.py实现完整编解码器原型**

**理由**: 在硬件开发前验证所有算法细节

**步骤**:
  1. 扩展脚本：实现条带切分、条带头生成、UDP封装模拟
  2. 实现闭环码率控制（Q自适应 + Mode 2降级）
  3. 用完整视频（非4帧采样）统计码率分布
  4. 验证解码器bit-exact还原
  5. 测量高熵内容（雪花噪声、纯随机）的最坏码率

**交付物**: Python参考模型 + 码率统计报告

**预计耗时**: 3-5天


### 🟡 P1 - 近期执行
**详细设计2路并行解码机制**

**关注点**: 当前描述"按偶/奇样本交错"存在歧义：
  - 若按像素位置交错：偶数列样本 vs 奇数列样本
    问题：MED需要左邻(a)，交错后a可能在另一路中
  - 若按扫描顺序交错：样本0,2,4,... vs 样本1,3,5,...
    问题：同样破坏空间局部性

**建议方案**:
  1. 编码端不做交错，正常生成位流
  2. 解码端用2个Rice解码器**流水线并行**，而非数据并行
     - Decoder 0处理样本i时，Decoder 1处理样本i+1
     - 吞吐加倍，但因果性保持
  3. 或者：每行分2半，左半行 vs 右半行独立编码
     - 行内预测需特殊处理边界

**行动项**: 画出数据流图，确认因果性不被破坏


### 🟢 P2 - 中期执行
**参考开源JPEG-LS实现，但勿直接移植**

**参考项目**:
- **FPGA-JPEG-LS-encoder (WangXuan95)** - 344 stars
  优点: MED预测器实现, Rice编码器, Verilog易读

## 五、技术细节待明确

以下问题需在详细设计阶段明确：

1. **条带头CRC32覆盖范围**
   - 问题: CRC32是否覆盖整个UDP净荷（含条带头本身）？
   - 现状: 文档未明确
   - 建议: CRC应覆盖条带头(除CRC字段外) + 数据载荷

2. **帧序号循环处理**
   - 问题: frame_id 16bit，循环周期 = 65536/60 = 18分钟，如何处理翻转？
   - 现状: 文档未提及
   - 建议: 解码端需实现模运算比较，允许±32768范围内的序号

3. **tile_id与平面关系**
   - 问题: 405个条带如何映射到(frame_id, tile_id)？
   - 现状: 文档说0..404，但未说明Y/Cb/Cr如何区分
   - 建议: 明确编号规则，如 Y:0-134, Cb:135-269, Cr:270-404

4. **色度上采样方法**
   - 问题: 4:2:0→4:4:4用什么插值？
   - 现状: 文档未说明
   - 建议: 最简单：最近邻（复制）。若要质量：双线性插值

5. **量化Q的数值范围**
   - 问题: Q=1,2,4,8,16是否足够？Q=16时质量如何？
   - 现状: 文档只实测到Q=4
   - 建议: 补充Q=8, Q=16的PSNR实测

## 六、数学验证摘要
═══════════════════════════════════════════════════════════════════════════

以下关键计算已验证正确：

✅ 原始码率: 1920×1080×60×1.5×8bit = 1493 Mbit/s
✅ 1GbE有效载荷: 957.1 Mbit/s (MTU1500, 95.71%效率)
✅ 压缩比需求: 1493/957.1 = 1.56:1
✅ 总采样率: 186.624 Msample/s (解码器吞吐瓶颈)
✅ Mode 2硬上界: 6.00 bit/px = 746.5 Mbit/s = 78% 1GbE
✅ 行缓存: Y平面 2行×1920 = 3840B = 3.75KB (峰值)
✅ UDP包速率: 45.5 kpps (占千兆上限81kpps的56%)

⚠️ 压缩比声明: 文档称"2.3:1"，实际应为2.82:1 (12.00/4.26)
