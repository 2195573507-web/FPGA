# `tile_decoder` 吞吐缺口与候选路线

> 生成时间 2026-10-16。工作目录 `D:/FPGA`。本文的算术全部可在文末 §7 复现。
> **证据强度分级（全文遵守）**：`[实测]` = 已跑出的日志/命令输出；`[算术]` = 由实测参数推出的算式；`[候选]` = 未实施的设想。**没有一条结论经过硬件验证。**

## 0. 一句话结论

1. **1080p60 未达标。** 一帧 3,110,400 个样本，`tile_decoder` 在 125 MHz 下单实例 **理论上限 40.1878 fps**（理想 1.000 样本/拍 = 24.883 ms）；intg0 仿真拍数 3,121,057 拍（0.997 样本/拍）按**同一设计时钟 125 MHz 换算**得 **40.0505 fps**（24.968 ms）。这两个数都是**仿真拍数 ÷ 设计时钟**的换算值，**不是上板实测帧率，也不是端到端 E2E 帧率**（见 §1.2 表内分级）。帧周期 16.667 ms，缺口 8.2~8.3 ms。
2. **缺口不可能靠「提高 0.997 到 1.000」解决**：那只有 0.3% 的差别，即使理想化也只有 40.19 fps，仍远低于 60。**0.997 与 1.000 之争是伪问题。**
3. **但它不是端到端的第一瓶颈。** 主机 ioctl 通路**实测**只有 **720p XRGB8888 约 3.755 fps**（`docs/host_side_changes.md:161-181`，13.2019 MiB/s = 13,843,195 B/s ÷ 3,686,400 B/帧，2026-10-14 历史记录）。**1080p 没有实测**：按同一速率线性外推，RGB888 约 2.225 fps、XRGB8888 约 1.669 fps（`[算术]`）。无论取哪个数，主机通路都比解码器差一个数量级，**解码器并行化不是端到端实时的充分条件**。
4. **本轮不实施任何并行重构。** 双实例 round-robin 只是**候选路线**；`12.4416 ms` / `25.35%` 这类数字是**理想算力的算术结果**（`25.35%` 按 P3 口径是「总计算预算余量」），不是已实现或已验证的性能。`tile_buf` 单读口的数据分发/重放、两路输出重排与背压（**下游合并后仍受 1 样本/拍 = 需 1.492992 样本/拍的限制**）、行缓存带宽、帧隔离/错误恢复、资源与综合时序**都还必须另行设计与验证**（§3.2 共 7 项）。
5. `rtl/tile_decoder.v` 在 t9 合同里是 **outOfScope**——任何并行化都需要先立新任务。

```bash

# 期望: 总拍=3121057 单条带最大=15651 (tile=1) 平均=11516 样本/拍=0.997
```

### 1.3 那多出来的 10,657 拍

```
3,121,057 − 3,110,400 = 10,657 拍
10,657 / 271 条带 = 39.3247 拍/条带   （算术平均）
```

**这是算术平均，不是归因。** 没有证据表明这 10,657 拍「全部属于条带启动/收尾开销」——也可能包含握手间隙、`tile_buf` 回放等待、或位流对齐损失。要归因必须逐条带测量（例如按条带打印起止拍），本轮**没有做**。本文只把它记作「每条约 39.3 拍的未归因开销」。

### 1.4 结论

**1080p60 在单实例下不成立**，且缺口（8.2~8.3 ms）**与 0.997/1.000 无关**。

## 2. 端到端的第一瓶颈不是解码器

`docs/host_side_changes.md:19` 结论摘要第 5 条：现有 ioctl 提交 4080 B + `copy_to_user` 取回的主机通路实测 **13.2 MiB/s**。

`docs/host_side_changes.md:161-181` 的原始实测行：

```
PASS frames=1 bytes=3686400 chunks=1800 mismatch=0 seconds=0.266297 MiB/s=13.2019
1800 chunks x 2048 B = 3686400 B; 平均 147.9 us/chunk
```

换算（`13.2019 MiB/s = 13.2019 x 1048576 = 13,843,195 B/s`）：

| 分辨率/格式 | 帧字节 | 换算 | 帧率 | 证据强度 |
|---|---|---|---|---|
| 1280x720 XRGB8888（单 DWORD/像素） | 3,686,400 B | 0.266297 s/帧 | **3.755 fps** | `[实测]`（原始样本） |
| 1920x1080 **RGB888**（3 B/px） | 6,220,800 B | 0.4494 s/帧 | ≈ **2.225 fps** | `[算术]` 由同一速率线性外推，**未实测** |
| 1920x1080 XRGB8888（4 B/px） | 8,294,400 B | 0.5992 s/帧 | ≈ **1.669 fps** | `[算术]`，未实测 |

**注意两种格式不能混用**：1920x1080 RGB888 是 `1920 x 1080 x 3 = 6,220,800 B`，不是 8,294,400 B（后者是 XRGB8888，`1920 x 1080 x 4`）。此前 `docs/host_side_changes.md:174`、`docs/top_integration.md:205` 与本文件旧版本把 8,294,400 B 标成 RGB888 并算出 3.3 fps，**三处均已更正**。

若把 ioctl 从 2 次压到 1 次 + `mmap` 去掉 `copy_to_user`，速率可望提到约 20 MiB/s 量级 —— 这是**基于提交次数减半的假设推算，未实测**；即便成立，仍差 20 倍以上。

**因此**：把 `tile_decoder` 并行化到 60 fps，并不能让端到端达到 60 fps。这一条已写进 `docs/top_integration.md` §6.4。

## 3. 三条候选路线

### 3.1 路线 (a) —— 标注上限，不改 RTL

| 项 | 内容 |
|---|---|
| 做法 | 在文档与模块头部显式写明「单实例上限 40.1878 fps（理想）/ 40.0505 fps（intg0 仿真拍数按设计 125 MHz 换算），1080p60 不达成」——两个数都是换算值, 不是上板/实测帧率 |
| 代价 | **0**（纯文档） |
| 后果 | 1080p60 不达成。端到端另受主机通路限制：**720p XRGB8888 实测 3.755 fps**；**1080p 没有实测**，按同一速率线性外推约 **RGB888 2.225 fps / XRGB8888 1.669 fps**（`[算术]`，见 §2）。**不得把 720p 的 3.755 fps 当成 1080p 的当前端到端上限。** |
| 判定 | **这正是 P3 采纳的交付边界**：明确记录单实例上限与 1080p60 未完成，**而不是在本次缺陷修复里偷偷实现双路**（`tile_sink.v:26-30` 的吞吐缺口自述即本路线的产物）。但「写明」不等于「达标」——**1080p60 仍未实现**；实时化必须另立任务（见 §3.2 / §4）。 |

### 3.2 路线 (b) —— 例化 2 个 `tile_decoder`

#### (b1) 按平面分：**已判定为陷阱，不要采用**

| 臂 | 样本 | 条带 | 拍数 = 样本数 + 条带数 x **假设的** 39.3247 | 时间 | 余量 |
|---|---|---|---|---|---|
| Y 实例 | 2,073,600 | 135 | 2,073,600 + 135x39.3247 = **2,078,909** | **16.631 ms** | 16.667 − 16.631 = **0.035 ms = 0.21%** |
| CbCr 实例 | 1,036,800 | 136 | 1,036,800 + 136x39.3247 = **1,042,148** | **8.337 ms** | 8.330 ms = 49.98% |

> **这两行不是「理想算力」，而是「样本数 + 假设的条带开销」。** 39.3247 拍/条带是**未归因的算术平均**（§1.3），不是实测到的每一条带开销；把它乘上条带数得到的是**带假设的预算**，不是测量结果。**去掉这项假设后**（只算样本数），Y 臂是 2,073,600 拍 = **16.5888 ms**，余量 0.0782 ms = **0.469%**——仍然几乎没有余量。两种口径都否决 (b1)，但**引用时必须说明用的是哪一种**。

`[算术]` Y 臂余量在 0.21%（含假设开销）到 0.469%（不含）之间——**没有任何实现余量**（时钟抖动、仲裁、FIFO 深度都会吃掉它）。否决。

#### (b2) 条带奇偶 round-robin：**候选路线，未实施未验证**

**思路（`[候选]`，未实施）**：分流器按条带计数器奇偶把 `tile_buf` 弹出的条带送给两个实例，两路的 `out_valid/out_pixel/out_x/out_y` 按条带归属合并。

> **先纠正本文件旧版本写过的两个不能成立的说法（已删除）**：
>
> 1. **「码流天然按条带交织 ⇒ 条带级分流无需像素级仲裁」没有证据。** 条带计数器只能告诉你「收到过 271 条带」（`[实测]` `tile_ready=271 / tile_y=135 / tile_c=136 / band=68`），**不能推出到达/完成顺序天然交错**；而且这条说法与 §3.2 末「`sd_stream` 只吃一路、`dec_out_*` 必须合并成有序单流」自相矛盾——**条带级分发不等于输出侧不需要仲裁与重排**。
> 2. **即使两实例算力之和足够，下游输出仍是 1 样本/拍。** 每实例上限 1 样本/拍（`rtl/tile_decoder.v:241-281`），两路合并回单流后仍受同一个 125 MHz 单流带宽约束：合并后的单流要在 16.667 ms 内送出 3,110,400 样本 = **186.624 Msample/s = 1.492992 样本/拍 > 1**。**所以「输出序列化」本身就是一条独立的 125 MHz 瓶颈，与解码算力无关。**

**理想算力（不含条带开销，`[算术]`）**——按实际条带大小逐条算，**注意奇偶分流并不天然均衡**，因为 Y 条带 15360 样本、C 条带 7680 样本（末条 3840）。

> **本小节的成立前提（必须一并引用）**：下面 1,559,040 / 1,551,360 的分配**只在「全局条带序号 0..270 固定为 135 个 Y → 68 个 Cb → 68 个 Cr、且按序号奇偶轮转」这一假设下成立**（`_tmp/P3_THROUGHPUT_VERDICT.md` 的原话：**「这不是任意到达顺序的负载保证」**）。若实际到达/完成顺序是乱序的，奇偶两臂的样本数会随调度改变，**本文不给出任意乱序下的上界**。

| 全局条带序号 | 归属 | 组成 | 样本数 |
|---|---|---|---|
| 0..134 | Y | — | — |
| 135..202 | Cb | — | — |
| 203..270 | Cr | — | — |

偶序号臂 = Y 偶 68 条 x 15360 = 1,044,480；Cb 偶 34 条（含末条 3840）= 33x7680 + 3840 = 257,280；Cr 偶 34 条（含末条 3840）= 257,280 ⇒ **1,559,040 样本**。
奇序号臂 = Y 奇 67 条 x 15360 = 1,029,120；Cb 奇 34 条 x 7680 = 261,120；Cr 奇 34 条 x 7680 = 261,120 ⇒ **1,551,360 样本**。
（校验：1,559,040 + 1,551,360 = 3,110,400 ✔）

| 量 | 偶序号臂（最坏） | 奇序号臂 |
|---|---|---|
| 样本数 | 1,559,040 | 1,551,360 |
| 理想拍数（1.000 样本/拍） | 1,559,040 | 1,551,360 |
| 理想时间 | **12.472 ms** | 12.410 ms |
| 加**假设的**条带开销（136 条 x 39.3247 = 5,348 拍 = 0.0428 ms） | **12.515 ms** | 12.453 ms |
| 余量 vs 16.667 ms | 4.152 ms = **24.91%** | 4.214 ms = 25.28% |

> **这是一份「带假设的预算」，不是已验证的性能承诺。** 上表有两层假设：
>
> 1. **样本数**：按实际条带大小逐条统计（不是把 3,110,400 均分两半），这部分是确定的算术。
> 2. **条带开销 39.3247 拍/条**：这个数是从单实例实测的 `3,121,057 拍 - 3,110,400 样本 = 10,657 拍` 除以 271 条带**算出来的算术平均**，它**没有被归因到任何具体机制**（见 §1.3）。把它按 136 条线性放大到双臂，等于**假设该开销随条带数线性增长且不因并行而改变** —— 这个假设**没有任何测量支撑**。
>
> 因此 12.515 ms / 12.453 ms / 24.91% / 25.28% 只能读作「在假设开销线性可加时的乐观预算」。**并行路线的余量必须靠真实实现后的实测来确认**，本表不足以支撑「保证达标」的结论。
>
> **与 P3 当前裁定一致**：`D:/FPGA/_tmp/P3_THROUGHPUT_VERDICT.md`（2026-10-16 重写版）写「两实例理论平均均分为 1,555,200 样本/臂，理想 12.4416 ms；**25.3504% 仅总计算预算余量**」，并明确「若特定源序列严格为 135Y→68Cb→68Cr，再按全局奇偶分配，考虑末色度条带只有 3840 样本，计算得 1,559,040 / 1,551,360 样本，两臂理想 12.47232 / 12.41088 ms。**这不是任意到达顺序的负载保证**」。
>
> 本文 §3.2 的逐条数字与该重写版一致：**1,555,200 是「总量均分两半」的粗算，1,559,040 是按实际条带大小逐条算的最坏臂**。两者都是 `[算术]`，差值 0.44 个百分点。**旧版草稿里被撤回的数字不再引用。**

**必须另行设计与验证的东西（`[候选]`，一条都没做）**：

1. **`tile_buf` 单读口的数据分发 / 重放**：`tile_buf` 只有一个读口（`rtl/tile_buf.v:263-264` 的 `q_pop` 与 `rd_next` 单路握手），两实例要各自拿到完整条带数据，必须先解决「一次弹出、两路消费」或「两路独立读指针 + 重放」。**这是本次最硬的接口改动，尚未设计。**
2. **输出重排与背压（含下游 1 样本/拍瓶颈）**：`sd_stream` 只吃一路、`frame_buf` 单写口。两实例并发时按条带归属的写入地址不冲突，但**合并回单流的顺序**必须与单实例逐字节一致，否则 L1 判据会破；而**合并后的单流本身仍受 1 样本/拍限制**（16.667 ms 内要送 3,110,400 样本 = 1.492992 样本/拍）。**这条瓶颈不会因为解码算力翻倍而消失。**
3. **行缓存带宽**：`tile_decoder.v:197` 每实例 1920 B x 8 bit = **15.0 Kb**；两实例 30.0 Kb。色度实例把 `MAX_W` 参数化为 960 可省一半 = 7.5 Kb。相对 `tile_buf` 的 256 Kb（32768 B）不算大，但**未做综合/布线评估**。
4. **分流器状态机与 `DRAIN_QUIET` 复制**：每个实例都要维护「上一条带是否吐完」（即 `tile_sink.v:195` 的 `DRAIN_QUIET` 机制复制两份），而 `DRAIN_QUIET=8` 本身的边界证明**尚未完成**（见 `docs/rtl_fix_code_review.md` §5.2），复制两份只会放大这个未验证风险。
5. **不触碰 `rtl/tile_decoder.v`**（t9 合同 outOfScope）：只新增例化与分流器。但分流器放哪里（新模块还是改 `tile_sink.v`）尚未决定。
6. **帧隔离 / 错误恢复**：`frame_ctrl` 的整帧丢失语义（条带越界 ⇒ 哨兵 `last_idx=5'h1F` ⇒ `frame_drop`）在两实例下要保证「同一帧的两路都不吐半个条带」，**未设计**。
7. **资源、综合与时序**：双实例 = 双份行缓存与数据通路；`rtl/tile_decoder.v:197` 的 `mem` 是否推断成 BRAM **未做综合评估**，双实例能否在 125 MHz 收敛**未做时序分析**。

### 3.3 路线 (c) —— 改成 2 样本/时钟：**已否决**

| 项 | 内容 |
|---|---|
| 收益 | 理想 12.442 ms ≈ 80.4 fps；「25.35%」是**总计算预算余量**（`_tmp/P3_THROUGHPUT_VERDICT.md` 口径），不是已实现性能，与 (b2) 同级 |
| 代价 | 改动**已回归的模块** `rtl/tile_decoder.v`（146 个向量）；t9 合同明文 (c) 必须先向队长申请新任务 |
| 难点 | FETCH 级是**变长码串行位流**（Rice：q 个 0 + 1 + k 位，见 `rtl/tile_decoder.v:159-178`），每拍消耗的位数取决于码字。2 样本/拍需要双位流游标或预解码缓冲 |
| 判定 | **否决**：(b2) 已达同一余量，而 (c) 的风险高一个量级 |

## 4. 建议

1. **本轮采用路线 (a)**：把 40.1878 fps（理想）/ 40.0505 fps（intg0 仿真拍数换算）与「1080p60 不达成」写进文档与模块头部（已写入 `docs/top_integration.md` §6.2、`docs/sfp_e2e_report.md` §9.5、`tile_sink.v:26-30`）。**这两处措辞中的「实测」若已写出即为过强表述**，正确口径是「仿真拍数按设计时钟换算」。**不实施并行重构**——P3 裁定明确要求「记录单实例限制和未完成实时化，而非在本次缺陷修复中盲目实现双路」。
2. **(b2) 是未来唯一有希望的候选**，但必须先做 §3.2 列的 **7 项**设计与验证；**`12.515 ms` / `24.91%` 是「样本数（确定）+ 假设的条带开销（未归因）」的预算，不得当作已达成性能引用**。
3. **不要 (b1)**（按平面分，Y 臂余量 0.21%）。
4. **不要在 t9 里改 `rtl/tile_decoder.v`**；路线 (c) 需另立任务。

## 5. 为什么 0.997 不是根因（澄清一个易犯的错误）

| 假设 | 帧拍数 | 时间 | fps | 相对 60 fps |
|---|---|---|---|---|
| 理想 1.000 样本/拍 | 3,110,400 | 24.883 ms | 40.1878 | 缺 19.8 fps |
| 仿真 0.997 样本/拍 | 3,121,057 | 24.968 ms | 40.0505 | 缺 19.9 fps（换算值） |

把 0.997 优化到 1.000 只能把帧时间从 24.968 ms 降到 24.883 ms——**省 0.085 ms，占缺口的 1%**。真正的缺口是「单实例只有 1 样本/拍的算力」。
